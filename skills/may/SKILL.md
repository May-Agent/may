# May

May is a daemon with clients. The daemon runs every agent loop, the task scheduler and search indexing; the TUI, one-shot runs (`may "<prompt>"`) and the web UI attach to it. This file states how the parts behave today. `references/architecture.md` lists where each part lives in the source.

## Product reference

What the user sees and sets. Read the file for the area a question touches.

- `references/slash-commands.md`: every TUI slash command and what it does.
- `references/configuration.md`: `~/.may/config.toml` settings, providers and setting up a model.

## Terminal

`terminal` runs a command in the session sandbox. `timeout` (seconds, at most 7200) is required; the command and its process tree are killed when it passes.

- Foreground window: a call waits 10 seconds. A command still running then moves to the background and the call returns its PID with the output so far. The 10 seconds is a fixed window, not a sign that something is slow. `background: true` detaches at once.
- A background command reports its completion to you as an event when it ends, and a finished command starts a new turn if the session is idle. Do not wait for it with `sleep` or by re-reading unchanged output; both are refused. Use `terminal_read` for new output, `monitor` to follow a command or file continuously, `terminal_input` to write to the stdin of a `background: true` job, and `kill <pid>` inside `terminal` to signal or stop a job.
- A job running past 40 minutes raises one long-running alert; check it with `terminal_read`.
- A foreground command reads end of file on stdin, including one promoted to a background task; `terminal_input` to it is refused. Only a job started with `background: true` has a stdin pipe, which never reaches end of file. The harness watches such a job and raises one "waiting for input on stdin" alert per blocking episode, which means the command is reading stdin, not that it is working. Send input with `terminal_input` or kill the job. Tools that read stdin when given no path (`rg`, `grep`, `cat`) block on a background job's pipe when nothing feeds them: pass a path or `</dev/null`.
- The working directory persists after a successful `cd`. It is reset to the session directory, with a "Commands now run in ..." alert naming the reason, when the last command failed, ended through `exit` or a signal, ended outside readable paths, or the directory vanished. Detached jobs never carry a directory.
- `~` and `$HOME` are the session directory, in every mode. Use absolute paths for host locations.
- Output over 16,000 bytes is stored under `outputs/` and you receive a head and tail preview with the file path; read the slice you need from the file. Source code may be shown folded and JSON as tab-separated text, only when output is cut. `raw: true` returns the exact bytes. `max_lines` (default 200, at most 800) sets the inline line budget.
- Modes: `default` runs in the heel sandbox and needs no approval; `unsafe` runs on the host and needs the user's approval per script (unanswered requests are denied after 30 minutes for the main agent, 3 minutes for a subagent). `location: "<name>"` runs the command on a configured SSH server instead of the home environment; the first command on a server asks the user.
- Network: sandboxed commands reach the network; only the user's `[preferences.network_policy]` setting (restricted, allow list, deny list) can narrow it.
- Writes are limited to the session directory, directories the user approved (`request_workspace`) and the memories directory. `TMPDIR` is the session's `tmp/`.

## Session directory

Each session has `~/.may/profiles/<profile>/sessions/<id>/`, which is the sandbox and the terminal's starting directory. Session ids are petname words.

- `tmp/` scratch; `files/` uploads and recalled files; `data/` session state; `outputs/` overflow and full command outputs, and `context-dump.md` after a context dump; `artifacts/` deliverables.
- To show a user a file, write it under `artifacts/` and emit `<artifact url="path/inside/artifacts" />` on its own line.
- `tasks.md` is the session's task document, at `$MAY_TASKS` in every command. A row is a short title line (the only text the sidebars show) plus optional indented detail lines. The `tasks` command, an ordinary program on the command `PATH` (not an IPC command) that edits the file directly, covers `add --title … [--detail …] [--section roots|doing|queued]`, `start <n>`, `finish <n>`, `block <n> <what>`, `unblock <n>`, `edit <n> [--title …] [--detail …] [--clear-detail]`, `note <text>`, `decide <text>` and `list`; rows are numbered from 1 over every section, as in the document shown to the model, and an edit that would break the format is refused with nothing written. The file stays editable by hand. An item waiting on an open `ask_user` question or anything else the run cannot resolve is marked `BLOCKING <request_id or reason>`; a mark naming a request that is answered or withdrawn no longer holds. When the user answers a question, the harness itself removes every `BLOCKING <request_id>` mark naming it from `tasks.md` (the rows are pending again) and the answer's reminder lists the rows it unblocked; the agent does not edit the file for this. A row's detail in the clients leaves out its `BLOCKING` line, which they show from the mark.
- `skills/` links to the profile's skills; `.may/memories` links to the global memories directory; `repos/<slug>` holds the session's private clones of repositories.
- Conversation state lives in the SQLite database `~/.may/history.db` (messages, transcript, context snapshots, runtime state, pending questions and permissions, issues, PRs, scheduled tasks), not in files. After compaction or a restart, recover work from `outputs/`, `data/`, `files/`, `artifacts/` and `tasks.md`.

## Daemon

- Listens on the unix socket `~/.may/daemon.sock` (mode 0600), which trusts the local user. TCP is optional: `[daemon] port` names the local listener `may gui`/`may rest` serve — the first such run picks a free port and pins it, a later run on a taken port fails until the config changes or the port is freed. A third loopback listener on a random port serves the same routes behind an identity check and is what `tailscale serve` forwards to for remote access. Addresses in `[daemon] listen` are applied live; a non-loopback address requires the peer to be identified through Tailscale (WhoIs), whatever the doc comment on `DaemonConfig.listen` says.
- `~/.may/daemon.lock` keeps it to one instance. Clients start it on demand and replace it when its build id differs, draining running turns first (30 seconds, then the runs are interrupted).
- `may daemon [install|uninstall|status|stop]` manages it; `may rest` runs it API-only; `may gui` serves its web UI and needs the `ui` build feature.
- A turn starts with `POST /api/sessions/{id}/messages` and is followed on the `/api/events` stream, which every client shares, with replay of the turn in progress for late subscribers. A client disconnecting does not stop a turn. `POST /api/chat/enqueue` takes mode `steer` (default; interrupts the current turn) or `queue` (runs after it).
- Configuration is `~/.may/config.toml`, applied live without a restart.
- One-shot runs mark the session non-interactive: permission prompts are refused instead of asked.

## Commands

Everything except the native tools (`terminal`, `terminal_read`, `terminal_input`, `monitor`, `compact`) is a command run inside `terminal`; each has `--help`. Positional arguments map only to required non-list fields; anything else is a `--flag`. The system prompt's command table is fixed for the warm prompt cache: a command added or removed mid-session (an MCP server connected, a skill registered) is announced once as a command-table change, and the table itself is rewritten only when the prompt is next reassembled.

- `ask_user "Which database?" --option PostgreSQL --option SQLite` asks one question — the positional form, equivalent to `--question "..." --option A --option B` (giving both is refused). `ask_user --questions '<json array of {"section","question","option":[...],"multi_select"}>'` asks a batch at once and overrides the single-question fields. For a credential never ask the value as plain text: `--secret <NAME> --secret-scope session|global`, or `"secret":{"name":"DEPLOY_TOKEN","scope":"session"}` inside `--questions`, asks the user only for the value, which is stored under that environment variable name and reaches your terminal commands as `$NAME`; scope `session` is deleted with the session, `global` reaches every session, and a secret question has no options. The call returns a request id at once; the answer arrives later as a message. `withdraw_ask_user <request_id>` closes a question. An unanswered question is not authorization.
- `search <query>` searches code in the session's git worktree by description; flags `--repo`, `--budget`, `--files`, `--path`, `--lang`, `--kind`, `--symbol`, `--wait`. The query `status` reports the index, `index` reconciles it. It is always hybrid (text and vector). Frequently searched repositories are indexed automatically by the daemon.
- `session search|find|inspect|messages|list` finds and reads past sessions; the subcommand and its argument are one quoted word (`session "messages <id>"`), and `--around <message id> --context N` limits `messages` to the N messages on each side of one (default 3).
- `session "find <regex>"` is rule-based search over session history, newest first, not the ranked index (it runs in the managed bash, which refuses the Unix `find`): it filters in SQLite (`--session-id`, `--role`, `--since`, `--until`, `--title-contains`), then runs the regex over message text. Flags: `--ignore-case`, `--context N` (neighbouring messages per match), `--count` (matching messages per session), `--tools` (also search tool calls and their output; off by default), `--limit` (default 20, at most 200), `--offset`. Thinking is never searched. A hit names its session and message id; read it in place with `session "messages <session>" --around <message id>`.
- `issue` (create, view, list, search, edit, comment, close, label, blocked-by, sub-issue) on the May backend by default, or GitHub / GitLab when the project is configured so (`--repo` targets another repository across `github:` and `gitlab:` bindings).
- `pr open|update|merge|list|show|close|adopt` lands work from a session workspace (its clone under `repos/`). One open PR/MR per workspace; `open` merges as soon as checks pass unless `--hold`; a failed check or conflict rejects it, so fix in the workspace, `pr update <n>` and `pr merge <n>` again. `repo trust set full|prs-only|local-branch|local` sets how far May may go for a repository, and `repo clone [--new]` derives a session workspace of it — `--new` always a fresh independent one, for concurrent PRs on one repository.
- `ci stats|slow <pr>|queue|log <job_id>` reports the CI durations recorded when a session PR's checks finish (per-job latest, median and p90, a PR's or run's jobs, steps and tests against their baselines, and merge-queue wait against run time) and fetches a recorded job's log over `ForgeAuth` without leaving the sandbox.
- `task` creates scheduled tasks (time, event or webhook triggers) that need the user's approval; `tunnel` exposes a local port; `browser` drives the May-managed browser; `webfetch` reads a URL (not present when the provider hosts fetching); `ask` asks a smaller model about content, so `webfetch <url> | ask "<question>"` returns only the answer for a large page (`rg` or `head` serve a known string or section); `imagine` generates images; `explore --prompt-file <path>` runs the bundled read-only `explore` subagent on the fast model; `computer <action> ...` sees and drives the session's virtual desktop, registered when the session may own one; `agent list|send <name> <prompt-file>` messages other main agents on this machine; `register-skills` registers a local skills directory; MCP servers the user connected appear as commands.
- Web search is a tool the model provider runs; there is no `websearch` command.

## Skills

A skill is a directory with `SKILL.md` (frontmatter `name`, `description`, and optionally `requires-command`: the system prompt lists the skill only in sessions where that command is registered, as with the bundled `computer` skill for the session desktop) and optional `references/` and `assets/`. The system prompt lists each skill's name and description; read the `SKILL.md` before acting on a matching request. Bundled skills are compiled into the binary, written to `~/.may/skills/` at startup (overwriting, so local edits to bundled skills are lost), copied into each profile's skills directory, and linked into the session as `skills/`. Skills can also be installed from a forge repository's `skills/` directory — GitHub as `owner/repo` or `github:owner/repo`, GitLab as `gitlab:<host>/<group/.../repo>`, plus clone URLs; a private repository clones over HTTPS with its `[forge."<host>"]` credential.

## Subagents

`subagent <name> --prompt-file <path> [--worktrees ...] [--commit-worktrees ...]`, `subagent resume --id <n> --prompt-file <path>`, `subagent fork --prompt-file <path>` and `subagent external --agent <name> --prompt-file <path> [--worktrees ...] [--commit-worktrees ...]`; `subagent` alone lists the names. A bare `subagent` runs nothing. The prompt is always a file you wrote first; inline prompt text is rejected. Each name is a definition in `~/.may/subagents/<name>.toml` (rewritten at startup) or in `agents/` under the working directory. Bundled: `explore`, `research` (fast, read-only), `audit`, `review`, `plan` (advanced, read-only) and `general` (the fast model routes each brief to a tier; writes the granted worktrees). The tiers run on the models `ask --model` offers. Every subagent, a connected agent and the commands it runs included, reads the workspace and writes only its own working directory, plus the worktrees granted to a definition that allows it. A resume id expires with the provider's prompt cache. Subagents cannot use `ask_user` or `agent`; for them `issue`, `pr` and `repo` only read. Write access beyond their own space comes only from `--worktrees` and `--commit-worktrees`, and their commits are listed in the result.

## Repositories, PRs and CI

Work on a git repository happens in a clone inside the session, and `pr` lands it. A session writes the user's checkout only through `pr`.

### Clones

- A session starts with no clone; workspaces are derived on demand at `repos/<name>-<8 hex>` (a second workspace of one repository gets `-2`, then `-3`, ...) and recorded in the history database. `repo clone` run inside a checkout (or `repo clone --path <dir>`) derives a workspace and prints its path; run again, it names a clean workspace still current with its source, and `repo clone --new` always derives a fresh independent one — the way to hold concurrent changes, one open PR each, on the same repository. With trust `full` or `prs-only` and a GitHub or GitLab remote, the workspace is a copy-on-write derivation of the daemon's default-branch checkout `~/.may/checkouts/<slug>/current`, refreshed against the remote first (carrying HTTPS `[forge."<host>"]` credentials when configured) and keeping its `upstream` remote; otherwise it is a `git clone --local --no-hardlinks` of the checkout (objects copied, `origin` is the checkout path). A repository with no trust decision, or with trust `local`, gets no workspace: run `repo trust set full|prs-only|local-branch` inside it first. `repo trust` acts on the repository the command runs in, or on the launch repository when run inside the session directory. A session the launch gate binds over a checkout's work in progress starts with a workspace whose base commit carries that work (`session_repo_clones.base_sha`), so the session's own commits begin after it.
- Run inside a workspace, `pr` acts on that workspace's repository. Elsewhere, pass `--repo <repo key or workspace directory name>`; without it `pr` takes the one workspace matching the directory the command runs in or the session's binding — deriving one on demand when there is none — and refuses when several fit.
- A workspace does not persist. It is deleted when its PR merges (the directory and its registry entry; for a local PR the checkout's `refs/may/pr/<n>` ref, for a GitHub or GitLab PR its remote `may/*` branch) and when the session is deleted. Merging a PR deletes only that PR's workspace. Ignored files such as build output go with it. Persist work by committing it in the workspace, or by writing it outside under `artifacts/`, `outputs/`, `data/` or `tmp/`. A workspace holding commits the PR did not land is kept. After a merge, `repo clone` derives again from the new HEAD.
- `pr open`, `pr update` and `pr merge` refuse while the workspace has uncommitted changes or untracked files that are not ignored, and list them. Commit them or move them out.

### PRs

- `pr open [--hold] [--issue <n>] [--title <t>] [--repo <key>]` records the PR and, without `--hold`, runs `pr merge` at once and returns when that ends; `pr.auto_merge = false` on the project holds the same way, and `pr.require_review = true` leaves the merge to the user — an agent `pr merge` is refused. `pr merge <n>` is also the retry after a failure or rejection. A PR owns the commit that was the workspace's HEAD when it was opened; later commits or a rebase in the workspace reach it only through `pr update <n>`. `--issue <n>` links an issue: a remote project's PR/MR body carries `Closes #n`, and a merge closes a linked May issue. `pr list [--state open|merged|closed|all]`, `pr show <n>` (with the event trail and the live checks), `pr close <n>` for your own unmerged PR, `pr adopt <n>` to take over a PR whose session is gone or that another session owns.
- One open PR per workspace. `open` needs committed work in the workspace (HEAD different from the base); `repo clone --new` derives a second workspace of the same repository, so one session can hold parallel PRs on it.
- Remote PRs and MRs store their true upstream number in `prs.number` (rendered `#N` for GitHub and May, `!iid` for GitLab; CLI arguments accept plain digits or a leading `#`/`!`); local May PRs allocate sequential per-repository numbers. Every transition (opened, checks_pending, merging, queued, merged, rejected, check_failed, closed) is a `pr_events` row with the session id, the actor (`main` for the agent, `user` for a client's own action) and the time; the agent's rows record the session's newest `message_id` at the time, so an event traces back to the message that caused it.
- Local backend: the project's `checks` command (`[[projects]]`) runs on a detached checkout of the PR's commit, which is held in the checkout as `refs/may/pr/<n>` until the PR lands or closes (it survives the session). Then, serialised per repository, `git merge-tree --write-tree` looks for conflicts, a file the user has modified in the checkout that the PR also touches is refused, and the merge is a `--no-ff` merge commit on the checkout's current branch. A conflict or overlap rejects the PR and lists the files: rebase in the workspace, `pr update <n>`, and run `pr merge <n>` again.
- Remote backends (`github` and `gitlab`): a remote-sourced workspace publishes through its forge over `ForgeAuth` (never spawning `gh` or `glab`); a local one merges into its checkout (a `[[projects]] pr.backend = "may"` pin on a remote workspace is refused, there is no checkout). The PR's commit is pushed to `upstream` as `may/<session>-<12 hex of the commit>` at open and update — the push leaves a bare staging repository that fetched the commit, carries `HostGit` HTTPS credentials when configured, and verifies every commit of the range against the user's signing key first. Before anything leaves the machine the outbound publish review (`PublishReview`) screens the title, body and commit messages together: stored secrets, host names and home paths are refused locally, then the fast model judges the text, and a block or an unavailable review refuses the publish (`pr.screen = true` persists the `prs-only` trust mode's screening decision). GitHub opens via REST `POST /repos/{owner}/{repo}/pulls` and queues via GraphQL `enablePullRequestAutoMerge` (`expectedHeadOid`, falling back to immediate REST squash merge when auto-merge is disabled and checks are already green); GitLab opens via `POST /api/v4/projects/:id/merge_requests` and queues via `PUT /merge_requests/:iid/merge` (`sha`, `squash`, `auto_merge`). A head upstream that is not the pinned commit fails the merge before it queues — run `pr update <n>` again.
- Watching and sync: `merge_watch` (`src/pr/merge_watch.rs`) follows a queued GitHub PR or GitLab MR until it merges, is closed, is removed from the merge queue/train or fails a required check; the bound is derived from the repository's recent successful runs scaled by the stages still ahead, and on it the call ends with the PR still queued — `pr merge` watches it again. On `MERGED`, pull-sync (`src/pr/pull_sync.rs`) runs `git pull --ff-only` on every local checkout recorded for the repository — `pr.pull_sync = false` turns it off and failures are reported in the result, never blocking — the daemon checkout is refreshed, and the workspace and the `may/*` branch are deleted (a branch the repository already deleted counts as deleted; any other failure is reported). Independently of a merge call, the daemon (`src/daemon/pr_checks.rs`) polls every in-flight GitHub PR and GitLab MR on `[ci] pr_poll_seconds`: the newest read backs `pr show` and the clients' PR rows, a change pushes `prs.changed`, and a rollup move — a failure, all checks green, the checks unreadable — stores one alert the agent is handed once.

### Subagents and repositories

- Subagents cannot push or open PRs. In the subagent command registry (`configure_role_tools` in `src/terminal_commands.rs`) `pr` accepts only `list` and `show`, and `repo` and `issue` only read. The main agent reviews a subagent's work and opens the PR itself.
- A subagent writes only where `subagent` granted it: `--worktrees` (writable to it, no commits) and `--commit-worktrees` (it may commit there, on a `subagent/<id>/` branch). Its commits are listed in the result; read them with `git log` and `git diff` before bringing them into the clone `pr` lands.
- A subagent run launched while the caller's working directory sits inside a session clone gets an isolated child clone named `repo` inside the run's own space automatically (`SessionSubagentSpaces` in `src/agent/subagent_spaces.rs`, `SessionRepos::child_clone`): a clone of that workspace at its current commit, so the run's work is `git diff base..head` of it and reaches the session clone only when you fetch and merge it. A run launched anywhere else gets only its writable directories.
- Not implemented (May-Agent/aither#206): approval of a subagent's `unsafe` command by its parent. Today the request is attributed to the parent's session and goes to the user, who has 3 minutes before it is denied; the parent neither sees nor decides it. A subagent that needs host access should say so in its result so the main agent can run the command.

## Memory

`~/.may/memories/MEMORY.md` is an index you maintain by editing files under that directory; link only to files inside it. Separately, a background extractor refreshes each profile's memories (`preference` and `recency`) at most every 24 hours, and they are placed in the context under `## User Preferences` and `## Recent Context`.

## Context and compaction

The conversation is compacted into a handoff document in the background when you call the native `compact` tool, when usage nears the window less the context policy's `handoff_reserve`, when the session has been idle until the provider's prompt cache (default one hour, the provider's `cache_lifetime` setting) is about to expire, or when the user runs `/compact`. The `compact` tool ends the turn: the compaction runs after it, no turn is served meanwhile, and the next turn starts on the handoff. The idle session's agent is kept between turns and reused unless something it was built from changed, so detached commands keep running. `/context` and `/btw` are answered without disturbing the conversation.

## Defects to know

- The "descendants were killed" alert points to a `terminal_background` command that does not exist; use `background: true`.
